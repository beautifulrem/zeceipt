# Data model, adapters, exports and contracts

## 1. Console data model (SQLite via better-sqlite3, Drizzle)

Storage is one SQLite file per deployment. Writes are synchronous `BEGIN IMMEDIATE` transactions; the file runs in WAL mode with `synchronous = FULL` and foreign keys on. libSQL's local client was rejected after a reproduced durability defect: after a busy error, later writes are silently not committed `[R47]`. Integrity is enforced by the schema itself (composite keys, CHECKs, conditional updates, triggers), never by check-then-insert or in-process locks, which are the competitor mistakes in `[R46]`. The execution ledger is protected by triggers (REQ-CON-7). A submission is never deleted, and its identity (org, nonce, batch, digest) never changes; its state, txid, attempts and bounds change only through the store's compare-and-set. The txid index is insert-only: never updated, never deleted, first entry wins. `INSERT OR REPLACE` of an existing ledger row or index entry is a no-op, and a batch is frozen once a submission exists for it.

Money: integer zatoshi (`bigint`) and integer USD cents. Rates: decimal string + source + ISO timestamp. All tables carry `org_id`. All tables carry `created_at` and `updated_at` except three: the two append-only ledger tables `submission_claims` (which carries `claimed_at_ms`) and `submission_txids`, and `batch_items`, which inherits its batch's timestamps (items are written once, with the batch).

Batch status is derived, never stored (built, slice B3: `lib/data/status.ts`, table in `.trellis/tasks/09-23-batch-status/design.md` §3.3.1.3.4.2). It is computed from the submission record, the chain status and the receipt count, so it cannot drift from them. The states are `draft`, `approved`, `submitting`, `retryable`, `needs_attention`, `pending`, `confirming(n of N)`, `confirmed`, `receipts_partial`, `receipts_issued`, `expired` and `voided`, each with a next action (`approve`, `submit`, `wait`, `issue_receipts`, `resend_expired`, `record_expiry`, `investigate`, `none`). The reader uses the execution backend's own nonce store and in-flight window, so the status never disagrees with what `submit` will do. It fails closed: only a mined transaction with N confirmations counts as confirmed. The names follow Stripe's PaymentIntent lifecycle `[R54]` and PayPal's batch/item statuses `[R48]` (REQ-CON-7, REQ-CON-11). `approved` (slice I3) is a draft with a valid approval of the batch as it is now; a draft, or a `retryable` batch re-locked since its approval, has next `approve`. `cancelled` arrived as `voided` (slice H5c).

## 2. Execution-backend adapter contract

```
trait PayoutBackend {
  fn name(&self) -> &'static str;                       // "zkool-graphql" | "zallet-rpc" | "zip321-manual"
  async fn preflight(&self, batch) -> Result<Preflight>; // balance, address validity, memo length ≤ 512 bytes
  async fn submit(&self, batch, nonce) -> Result<Submitted { txid | uris: Vec<String> }>;
  async fn status(&self, txid) -> Result<TxStatus { Pending | Mined{height} | Unknown }>;
}
```

| Backend | Mechanism | Notes |
|---|---|---|
| zkool-graphql (primary) | `mutation pay(idAccount, payment:{recipients:[{address, amount, memo}], srcPools, confirmations})` → txid; poll `transactionsByAccount(idAccount, height)` for `height > 0` `[R18]`. Measured on regtest 2026-09-22 (PROOF §5b): run `zkool_graphql --coin 2 --lwd-url <zaino> --no-mempool`; pool bits transparent 1 / sapling 2 / orchard 4 / **ironwood 8**; amounts are decimal strings in ZEC; memo > 512 bytes rejected before signing; 3 recipients + change land in one v6 tx; restore the issuer with `useInternal: true` or notes at the internal scope are invisible | seed lives only in the Zkool process; app holds UFVK; built from source on this machine (no Docker), Docker image also available |
| zallet-rpc | `z_sendmany` with duplicate-address splitting; poll `z_getoperationstatus/result`; treat lost reply after spawn as Unknown `[R19]` | beta; open spend-path bugs |
| zip321-manual | one ZIP-321 URI per recipient (never multi-recipient: Zodl rejects `[R17]`); operator scans with YWallet/Zodl; txid entered manually or detected via UFVK scan | non-custodial |

Implemented in TypeScript as `apps/console/lib/execution/` (`PayoutBackend`, `ZkoolBackend`; stores `SqliteIdempotencyStore` for the console and `FileIdempotencyStore` for tools, both passing one contract suite; PROOF §5c). Zkool behaviours relied on are in `[R44]`; preflight's fee estimate follows ZIP 317 and its address checks ZIP 316 `[R43]`. Idempotency: an intent record is created exclusively per nonce *before* `pay`; a replay returns the recorded txid; only a known pre-build refusal from Zkool (e.g. "No feasible note selection found", "Not enough funds") leaves the nonce `failed_retryable` (retry claims the next attempt exclusively). Every other failure (transport loss, timeout, any other GraphQL error — Zkool reports a failed gRPC send that way even when the node may already hold the transaction — or a node rejection returned in place of a txid) leaves it `unknown_outcome` with `expiresBy` = node tip after the attempt + 40 (Zkool's expiry delta; a transaction cannot be mined above its expiry height) + a 10-block reorg margin. A later submit reconciles against the issuer's mined transactions by address + memo + value, up to the account's *scanned* height (Zkool's `synchronizeAccount` can return the node tip without scanning). Found → adopt the txid; not found and scanned height > `expiresBy` → the attempt can never be mined, so pay again under the same nonce; otherwise still unknown. Record writes are compare-and-set per attempt; retry claims are recoverable after `inFlightMs`, so a crash cannot wedge a nonce. An expired `broadcast` is re-sent only by the explicit `resubmitExpired` (residual assumption: RSK-21). `autoIssue` matches each receipt to its own item (memo, value, address via the CLI's `matched_only_to`, not change, no output claimed twice) and writes receipt files only after every receipt verified.

Receipt issuance is backend-independent (REQ-CON-11): after `Mined{height}` and N confirmations, `autoIssue` (`apps/console/lib/issuance/auto-issue.ts`) runs `zeceipt issue --only-to <each batch address> --ufvk-file …` (the allow-list is matched by shielded receiver in `zeceipt-core`), cross-checks one receipt per batch item (memo, value, payee address via the CLI's `matched_only_to`, never change, no output claimed twice), verifies each, and only then writes the files and returns; results will be stored in `receipts`.

## 3. Export formats (exact columns)

### 3.1 OpenZcash-compatible (`openzcash.csv`) `[R110]` `[R5]`

This export is REQ-INT-2, a Should requirement reduced in the solo branch to this export (leaf 3.3.3.2), built in slices X2a–X2c. Re-derived 2026-09-26 (slice X1) from OpenZcash's own "Export CSV", so a row from the console sits beside a row exported from openzcash.org in one spreadsheet. The first seven columns match OpenZcash's export in name, order and cell format; the last three are additive.

`Recipient,Detail,Category,USD,ZEC,Date,Status,Txid,Receipt,Rate`

| Column | Value | Format (as OpenZcash renders it) |
|---|---|---|
| Recipient | the line's label: the recipient's display name copied when the line was made, so a later payee edit never changes what was paid (slice X2b) | text; OpenZcash's cell also carries its row type and origin ("Grant from spreadsheet"), which the console does not have, so it writes the name alone |
| Detail | the line's memo (`batch_items.memo`), which is the payable's reference for a line made from a payable | text |
| Category | the payable's kind for a line made from a payable (`Milestone`, `Invoice`, `Bounty`, `Salary`); `·` for a line made on the form | text; OpenZcash's own categories (e.g. "Community") are editorial, so the two files' categories differ in kind |
| USD | the line's dollars | `$12,000` for whole dollars, `$227.50` otherwise (en-US currency); `·` for a line made on the form without dollars |
| ZEC | the line's zatoshi | comma-grouped ZEC, trailing zeros removed, no symbol (`0.14648356`, `1,234.5`) |
| Date | the day the payment went out, as OpenZcash's Date is: the UTC day of the submission's `broadcast_at`; for a payment adopted from the wallet's history (after a restore, PROOF §5f, or when an uncertain attempt is reconciled later) it is the day it was adopted, unless an earlier broadcast was recorded | `YYYY-MM-DD` |
| Status | `Completed` | OpenZcash's label for a paid milestone |
| Txid | the transaction id | 64 hex characters |
| Receipt | the receipt link (`https://<host>/r#<payload>`) | text |
| Rate | the batch's locked ZEC/USD rate for a batch made from payables, which converted its dollars into zatoshi (exactly one lock, H5a; planned under REQ-INT-2, with the lock of REQ-CON-4) | the stored decimal string; `·` for a batch made on the form, whose lines were set in ZEC, so no rate converted them |

- Cells (REQ-INT-2, a Should requirement): OpenZcash's seven follow its renderers' order: the renderer's `·` for an empty value first, then the clean-up its table applies to each rendered cell (whitespace collapsed to one space, trimmed). So a Detail cell shows the memo with its whitespace collapsed, a blank memo gives an empty cell as it does in OpenZcash's export, and the receipt keeps the exact memo. A blank recipient label gives `·`, the console's choice, since OpenZcash's Recipient cell is never empty. The three additive cells are written as they are.
- Rows: one per issued receipt, in batch order then line order; a line without a receipt (not yet confirmed, or not issued) is not a row, since a ledger row here means a verifiable payment.
- Encoding, as OpenZcash's: a UTF-8 BOM, CRLF line ends, every field in double quotes with `"` doubled, and the same formula guard: a field matching `/^\s*[=+@\-\t\r]/` and not matching `/^\s*[-−]?\$?\d[\d,]*(\.\d+)?(\s*[A-Za-z%]{1,4})?\s*$/` gets a leading `'` (so `  =x` is guarded and `-$1,200` is not); a header row.
- Disclosure: every Receipt cell carries that output's OCK, so the file shows each listed payment to anyone who holds it (THREAT_MODEL "A receipt link leaks"), and permanently: a receipt cannot be revoked (spec §9), so putting the file in a public ledger publishes those payments for good. It is made on an explicit request through the guarded API (GET only: HEAD is 405, since Next.js would run the GET handler for it `[R111]`; refused when `Sec-Fetch-Site` is cross-site or same-site), recorded in the audit log by an explicit insert (the log is otherwise written by triggers), never cached or written to disk by the console, and the page that offers it says so. The downloaded file on the user's disk is a new path for a link to leak; X2 adds it to THREAT_MODEL's row.

### 3.6 Import formats (REQ-CON-19, a Should requirement; slice I1) `[R112]` `[R113]`

Two formats that Zcash payers already export, each read from its project's own parser, each mapped to the console model that holds its unit. At most 50 rows (the batch limit B1, and `MAX_PAYABLES`), like Wise's cap per batch file `[R113]`. Every row the console cannot hold is reported by its source line (counted from 1 over the file's lines) with its reason, and the good rows are kept, as Konclave's own import does `[R112]`; no row is dropped silently.

**Header rows.** A first row is a header only when its fields are the format's column names (trimmed, case-insensitive). Anything else is parsed as data and, if bad, reported. This differs from Konclave on purpose: Konclave treats any first row whose third field is not a ZEC amount as a header and drops it without an error, so a headerless file whose first amount is mistyped (`0,5`, `1 ZEC`) would lose that row silently `[R112]`.

**Konclave, `label,address,value[,memo]` (ZEC) → the lines of a draft batch.** Rows are split as Konclave splits them (`orchestrator/src/payroll.rs`): blank lines skipped; each row split on its first three commas, so the memo is everything after the third (commas included) and no field is quoted; fields trimmed; an empty label allowed; `value` parsed as Konclave's `from_zec_str` parses it (digits and one point, `.5` and `5.` allowed, no sign, no separators, at most 8 decimals, at most the 21M ZEC supply) and greater than zero. Filling again skips a row whose line id or memo is already in the form, and says so. Each row becomes a draft line: label → label, address → address, value → amount, memo → memo, and a line id `row-<source line>`. The lines are filled into the draft batch form; nothing is created until the operator submits it, and the form's own rules then apply, so a row Konclave accepts can still be refused here, and says why: an address that is not a unified address with an Orchard receiver on this network, or a memo already used by another batch. Konclave's memo is optional and the console's is required (it is the payment's reference): an empty memo takes the operator's prefix for the file, then `-` and the source line, and the draft form marks each memo made that way.

**zecpay, `name,wallet,amount,currency,payout_currency` (USD) → payables.** Rows are read as zecpay reads them (`lib/csv-parser.ts`): a header row required and columns found by name (trimmed, case-insensitive); rows split on every comma; `currency` defaulting to USD and `payout_currency` to ZEC. Each row with `currency` USD and `payout_currency` ZEC becomes a payable. Its amount must be whole cents (stricter than zecpay's `parseFloat`, which reads `500abc` as 500). Its recipient is the existing recipient on this network with the same Orchard receiver (the console's "same place" rule, H1 and H6), else a new one named `name`; when the names differ the existing name is kept and the preview shows both. Its kind is the one the operator chooses for the file (default Salary, since zecpay is a payroll tool). Its reference is the operator's prefix, then `-` and the source line (`PAYROLL-2026-09-3`), since zecpay has no reference column and the console needs one to be the payment's memo; references are unique in the organisation, so a reused prefix is refused per row as "reference taken". Refused with their reasons, checked in this order so each row gives one reason: `currency` ZEC (a ZEC amount belongs in a draft batch: use the Konclave format) or anything but USD, a `payout_currency` other than ZEC (zecpay's code accepts any value; the console pays only ZEC), an amount that is not whole cents greater than zero, an address that is not a unified address with an Orchard receiver on this network (mixed case included; zecpay also accepts Sapling `zs` and transparent `t1` addresses; an all-upper-case address is lower-cased, as the recipient form does), a new recipient without a valid name, a reference the organisation already holds, a reference that is not valid (too long once the source line is added to the prefix), and more than 50 payables in the file.

**Preview, then confirm, for zecpay.** (REQ-CON-19, a Should requirement.) Payables and recipients are permanent records: no route edits or deletes them, and their trail is append-only (THREAT_MODEL, "A payee's address is swapped"). So the zecpay import first shows a preview (the parsed rows; each recipient matched or new, with any name difference; the references to be written; every refusal with its source line), writes nothing, and writes only on an explicit confirm, in one transaction: every accepted row or none. The Konclave import needs no separate confirm, since it only fills the draft form, which the operator submits.

## 4. Contracts

- Receipt envelope v0: `spec/receipt-v0.md` §2 (JSON), §5 (signing), URL form `/r#<base64url(json)>` (§2.1; payload in the fragment, the v0 path form `/r/…` still parsed; `[R66]`).
- Audit pack: `{"version":"zeceipt-v0","title","declared_total_zat","receipts":[…]}` (spec §8).
- **Well-known issuer keys** (`https://<domain>/.well-known/zeceipt.json`; spec §7; REQ-CORE-10, REQ-INT-3; planned for leaf 3.3.3.3, dropped in the solo branch and being added back: built: the CLI (slices W2a, W2b), the verify package (`checkIssuerBinding`, W3a) and the receipt page (W3b)). The design was redone in slice W1 `[R101]`: a domain-control binding, and the key id `<label>@<domain>` carries the claim.
```json
{ "version": "zeceipt-v0",
  "keys": [ { "key_id": "2026-09@pay.example.org", "pubkey": "<64 hex>", "note": "optional" } ] }
```
  - **Semantics:** the lookup only upgrades a result. A key id that is listed with the same pubkey is **confirmed**. A valid file without it gives **not listed**. Anything else gives **unknown**. None of the three affects cryptographic validity.
  - **The earlier contract is withdrawn.** It had `org`, `root_pubkey`, a root signature and validity intervals, but no verifier could know the root key, and intervals cannot be checked because a receipt carries no signing time.
  - **Lookup limits:** HTTPS on the default port, no redirects, 64 KiB, 10 s. Browsers need `Access-Control-Allow-Origin: *` from the server.
  - **The domain** is ASCII LDH only (`xn--` A-labels for internationalised names), looked up and shown exactly as written (review W1 round 1).
  - **One rule,** `claim` in `zeceipt-types::binding`, serves the CLI and (W3) the page through WASM. `spec/test-vectors/binding-claims-v0.json` is generated from it, and the Rust tests and the console's validator (`lib/issuance/key-id.ts`) are both checked against that file (slice W2a).
  - **The console's `ZECEIPT_ISSUER_KEY_ID`** accepts `<label>@<domain>` (W2a).
  - **The CLI** refuses a domain that resolves to a loopback, link-local or private address. A receipt's author chooses the domain, and the lookup must not probe the verifier's own network (W2).
  - **The receipt page's CSP** adds `https://*/.well-known/zeceipt.json` to `connect-src`, not `https:`: that path, on any HTTPS host. Measured in Chrome (W3b): another path and plain `http:` are refused, and the path with a query string is admitted (THREAT_MODEL, the link-host row).
- Console batch routes (built, slice D1; `docs/api/openapi.json`): `POST /api/batches` creates a draft from `{title, items:[{payableId, label?, address, zat, memo}]}` → 201 with `Location` (the org and network come from the deployment's config; unknown keys are refused); `GET /api/batches` (newest first, `totalZat`); `GET /api/batches/{id}`. Amounts are zatoshi as decimal strings both ways (totals can exceed 2^53). Errors are RFC 9457 `application/problem+json` with a `code` (`batch_invalid` carries every problem with its item index) `[R58]`. Every request needs a loopback `Host`; unsafe methods refuse cross-site `Sec-Fetch-Site` and a foreign `Origin` (pages: `proxy.ts`; API routes: `guarded()`, which keeps the live body stream so an oversize body gets 413 at once) `[R59]` `[R60]`.
- Hand-typed memos (slice H7): `POST /api/batches` refuses a memo with invisible characters or a space other than U+0020 (`memo_invisible` at its index; the rule H3 applies to references), at creation only: preflight is unchanged, so drafts made before can still be paid `[R78]`.
- Console recipient routes (built, slice H1; REQ-CON-2): `POST /api/recipients` `{displayName, address, kycStatus?, taxFlag?, settlementPref?, notes?}` → 201 with `Location`, a duplicate flagged in `duplicateOf` (not refused); `GET /api/recipients` (newest first); `GET /api/recipients/{id}`. An invalid value is 422 `recipient_invalid` with every problem and its `field` `[R75]` `[R76]`.
- Console payable routes (built, slice H3; REQ-CON-3): `POST /api/payables` `{recipientId, kind, usdCents, reference, sourceUrl?}` → 201 with `Location`; `GET /api/payables` (newest first); `GET /api/payables/{id}`. Types and shape are 400 `body_invalid` (a missing reference, a string amount, an unknown kind or key); values are 422 `payable_invalid` with every problem and its `field` (`usd_invalid`, `reference_invalid`, `recipient_unknown`, `source_invalid`); a reference already used in the org is 409 `reference_taken` with the holder's `payableId` `[R78]`.
- Console batches from payables (built, slice H5a; REQ-CON-3, REQ-CON-4): `POST /api/batches/from-payables` `{title, payableIds[1..50]}` → 201 with the batch, its lines (`usdCents` set) and its lock, and `rateFixed: true`. Checked before the quote: 422 `batch_invalid` with `title_invalid`, `payable_unknown`, `payable_repeated`, `payable_taken` (naming the holding batch); the quote failing is 502 `rate_unavailable` (nothing created); a conversion outside 1..2.1e15 zat is `amount_out_of_range`. A re-lock of such a batch is 409 `rate_fixed` `[R80]`.

- Console void (built, slice H5c; R82): `POST /api/batches/{id}/void` → 200 with the batch, `voided: {at}`, when it has no submission or only a `failed_retryable` one (nothing can have been sent; BTCPay cancels a payout unless it is InProgress or Completed); 409 `batch_frozen` otherwise, 409 `batch_voided` when already voided, 404, 503. `batch_voids(org_id, batch_id, voided_at)` is append-only; a voided batch takes no submission, retry, quote, receipt or change (triggers), and its derived status is `voided` `[R82]`.
- Console approval (built, slice I3; REQ-CON-5): `POST /api/batches/{id}/approve` `{confirmTotalZat, lockSeq}` names what the approver saw (BTCPay's approve names the payout `revision`). 201 with `{batchId, approval: {seq, approvedAt, lockSeq, approver}}` and `Location` (the status route); 200 with the existing approval when one is already valid (no second row); 409 `custody_external`, `batch_voided`, `batch_frozen`, `rate_not_locked`, `approval_stale` (re-locked since; the extension `lockSeq` is the current one); 422 `confirmation_mismatch`; 400; 404; 503. Submit refuses an attempt without a valid approval with 409 `not_approved`, nothing sent `[R87]`.
- Console batch history (built, slice I4): `GET /api/batches/{id}/history` → 200 `{batchId, events: [{id, at, action, detail}]}`, oldest first; 404; the batch page's History section says each event in words. Refusals that change nothing (`not_approved`, `confirmation_mismatch`) leave no event; the wallet's refusal (`failed_retryable`) and the guard's execution quote do `[R89]`.
- Console record trails (built, slice I4b): `GET /api/recipients/{id}/history` and `GET /api/payables/{id}/history` → 200 `{kind, id, events: [{id, at, action, detail}]}`, oldest first; a deleted record's trail stays readable; 404 (`recipient_not_found` / `payable_not_found`) when there is neither the record nor an event `[R91]`.
- Linkability (built, slice H6; REQ-CON-6): every batch answer carries `linkability: [{idx, disclosedBy: [{batchId}]}]`, the lines paying an address (the same Orchard receiver) that another batch's receipt already disclosed; every recipient answer carries `disclosedBy: [{batchId}]`. Computed on read from `receipts.recipient` (an Orchard-only UA per output), never stored `[R84]`.
- Automatic receipts (built, slice I2; REQ-CON-11): a worker started from `instrumentation.ts` issues receipts for every batch whose derived status says `issue_receipts`, through `issueReceiptsResponse` (idempotent per output; the button and the worker never record one twice), every `ZECEIPT_AUTO_RECEIPTS_SECONDS` (default 60; 0 off; hot custody only); passes never overlap `[R86]`. A batch that keeps failing is retried after 1, 2, 4, 8, 16, then every 32 passes (capped exponential backoff, no jitter: one worker), and its failure is logged when it starts or its code changes, not on every pass; a recovery is logged once (slice I2b `[R88]`), and so is a failing batch that someone else completes or voids meanwhile (slice I2c).
- Console submit and status (built, slice D2): `POST /api/batches/{id}/submit` with `{confirmTotalZat}` (must equal the batch total) pays once per batch nonce and answers 202 `{batchId, txid, replayed, via, status}` with `Location` pointing to the status route; a replay carries `Idempotent-Replayed: true`. `GET /api/batches/{id}/status` → `{batchId, state, next, detail}` (§1 derived status). Submit problems carry `thisRequest` (`sent_nothing` | `may_have_sent`: what this request did, provable from the code) and `batchStatus` (the status route: whether the batch was paid is only there): `preflight_failed` 422, `payment_rejected` 409, `outcome_unknown` 502, `submission_in_flight` 409 + `Retry-After`, `nonce_conflict` 409, `store_busy` 503 + `Retry-After`, `wallet_unavailable` 502, `custody_external` 409, `confirmation_mismatch` 422 `[R61]`.
- Console receipts (built, slice D3; REQ-CON-11): `POST /api/batches/{id}/receipts` issues one verified receipt per item when the batch's derived status is `confirmed` or `receipts_partial` (201 `{batchId, txid, inserted, existing, receipts}`, or 200 when this request recorded nothing new, e.g. it lost a concurrent race); `receipts_issued` → 200 with the stored receipts (no CLI run); `pending`/`confirming` → 202 `{state: "waiting", confirmations, required}`; other states → 409 `not_ready_for_receipts` with `state` and `next`; `issuance_failed`/`receipt_unverified` 502 (nothing recorded). `GET /api/batches/{id}/receipts` → the stored receipts `{idx, payableId, txid, pool, outputIndex, valueZat, recipient, memo, issuedAt, verifiedAt, url, receipt}` (or `openError`). `url`/`receipt` contain the output's OCK: a bearer link, `no-store`. Console receipts carry no challenge.
- Console health (built, slice C2): `GET /api/health` → `application/health+json`, `{"status":"pass","checks":{"sqlite:responsiveness":[{"status":"pass"}]}}` with 200, or `fail` with 503; `Cache-Control: no-store`; no version, path, org or dependency details `[R57]`.

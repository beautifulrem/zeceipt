# Zeceipt v0.1.0

The first release of Zeceipt: verifiable receipts for shielded Zcash payments. An organisation that pays in shielded ZEC can hand each recipient, auditor or public ledger a receipt for one payment. Anyone can check it against the chain, recovering exactly that output's recipient, amount and memo, **without being given a viewing key** and without learning about any other payment. The release has four parts: the receipt format, a Rust library and CLI, a browser verifier, and a self-hosted payout console that pays a batch in one shielded transaction and issues a receipt for each payment.

## Try it

About ten minutes, offline after the first build, with no wallet keys involved. The full list, including every test suite, is the README's "For judges" section. The core of it:

```bash
cargo build --release && Z=target/release/zeceipt && T=$(mktemp -d)
$Z keygen --out $T/issuer.key
$Z issue --raw-tx-file fixtures/synthetic-ironwood.hex --ovk "$(cat fixtures/synthetic-ovk.hex)" --label demo --key-file $T/issuer.key --out-dir $T/r
$Z verify $T/r/*.json --raw-tx-file fixtures/synthetic-ironwood.hex --require-signature
(cd packages/verify && npm run demo)    # the receipt page at http://localhost:8787/r/
```

## What's in it

The details, with where each part's evidence is, are in `CHANGELOG.md`, section `[0.1.0]`. Paths in these notes are relative to the repository root.

- **Receipt format v0** (`spec/receipt-v0.md`): an optionally signed envelope that discloses one output by its Outgoing Cipher Key. It supports:
  - challenges, for receipts made out to one verifier;
  - audit packs;
  - an optional domain binding for issuer keys;
  - receipt links that carry the receipt in the URL fragment.
  
  Test vectors are committed.
- **`zeceipt-core`, `zeceipt-lwd` and the `zeceipt` CLI:**
  - recovery for Ironwood (v6), Orchard and Sapling, using the upstream Zcash crates;
  - issue and verify, from a UFVK or an OVK, online or from a raw transaction file.
- **`@zeceipt/verify` and the receipt page:** the verifier compiled to WebAssembly, for the browser and Node. A page at `/r/` verifies a receipt link in the browser.
- **The payout console** (`apps/console`), bound to 127.0.0.1 by its npm scripts:
  - recipients, and payables in US dollars;
  - Konclave and zecpay CSV imports;
  - batches at a Kraken rate, with an approval bound to the lines, rate and paying account;
  - one Ironwood transaction per batch through Zkool, with a scoped token;
  - receipts issued automatically after confirmations;
  - an OpenZcash-compatible export;
  - an append-only history.

## What a receipt proves

**Proves:**
- the named transaction pays the shown value to the shown recipient with the shown memo;
- whoever produced the receipt knew that output's OCK. Deriving it takes the sender's outgoing viewing key, but anyone holding an earlier receipt for that output knows it too.
- if signed, the envelope is attributed to the issuer's key: a signature attributes the envelope to a key, not the OCK to its sender.

**Does not prove:**
- who is presenting it (use a challenge);
- anything about other outputs, transactions or balances;
- spend authority.

This is spec §4.

## Evidence

`docs/PROOF.md` holds each claim with its transcript:
- **mainnet (read only):** v6 parsing and Ironwood enumeration through the lightwalletd client (§1), and the issuer-binding lookup over the internet (§2d);
- **synthetic:** the issue → verify → tamper matrix, in the CLI and in Chrome (§2, §2b, §2c, §2e);
- **regtest:** a consensus-valid Ironwood transaction issued from the sender's UFVK and verified over gRPC (§5), a three-recipient batch built by Zkool (§5b), and the console end to end (§5c–§5g).

## Known limitations

Each comes from the spec, the threat model (`docs/THREAT_MODEL.md`) or the risk register (`docs/product/06_risk_register.md`).

- **Not a full ZIP 311 disclosure.** There is no spend-authority proof, which needs the spending key, and the tools never touch spending keys. So:
  - anyone with the sender's viewing key, or an earlier receipt, can make a receipt;
  - a receipt holder can re-sign one with their own key.
  
  Issuer attribution is an ed25519 signature (README; `docs/outreach/zips-387-comment.md`).
- **No receipts on a public chain yet.** The live evidence ran on a local regtest chain. Mainnet transactions have only been parsed and fetched. The testnet run waits on faucet funds (RSK-3; `docs/PROOF.md` §4).
- **The console has no sign-in.** It answers only loopback hosts, with no cross-site writes. But any local process that can reach its port can read every batch and receipt link, and in hot custody it can pay (RSK-24).
- **Double payment in narrow cases.** After an uncertain payment outcome, the console pays again only when nothing is mined past the attempt's expiry bound. That can still fail in two cases:
  - a stall inside Zkool longer than the pay timeout, followed by 40 or more blocks;
  - a reorg deeper than the margin (RSK-21).
  
  A database restored from a backup adopts a mined payment. One still unmined at restore time is not seen.
- **Change detection's residual cases.** Change is recognised by address ownership, and the console issues receipts only for its batch's recipients. For receipts issued outside the console, two cases remain:
  - a wallet that encrypts change to an address outside the issuer's viewing key would have it issued as a payment;
  - a legitimate payment to the issuer's own address is suppressed unless `--include-change` is given (RSK-20).
- **Lookups are visible to the node.** Fetching a transaction tells the node which one was looked up. The receipt page asks a node only when you click, or you can load a file instead (RSK-12).
- **Disclosure is permanent, and receipts to one address are linkable.**
  - A receipt can't be revoked.
  - It reveals that output's address to whoever holds it, and repeated receipts to the same address can be linked. Pay each recipient at a fresh diversified address (spec §9).
  - The console warns before paying an address an earlier receipt disclosed (RSK-11).
- **Hosting the receipt page is the deployer's job.**
  - Receipt links must use a host you control, because that host serves the page that reads the link's fragment.
  - The page's CSP is a `<meta>` tag, where browsers ignore `frame-ancestors`, so serve it with a `frame-ancestors 'none'` header, or it can be framed (README, "Hosting it"; `docs/THREAT_MODEL.md`).
- **Audit packs prove a lower bound.** A pack's total can't show that no payment was left out (spec §8).
- **A receipt without a challenge is a bearer document.** Anyone holding it can verify it and forward it (spec §6).
- **The console's secrets.**
  - The Zkool token is a bearer credential: whoever reads its file can pay from that account until it expires. Zkool speaks plain HTTP, hence loopback only.
  - The wrap keys are scrubbed from `process.env` after boot, but a copy survives in `/proc/<pid>/environ` and in Next's environment snapshot (RSK-23).
  - Recipients, addresses, memos and amounts are plaintext in the database; only receipts are sealed (`docs/THREAT_MODEL.md`).
- **NU7 transactions aren't supported yet.** NU7 (ZIP 259) adds consensus branch `0x77190AD9`, which the Zcash crates this release is built on don't know. Transactions made after NU7 activates (on testnet from the height set on 10-05, on mainnet from the height set on 10-20) are refused with an error naming NU7. A later release built on Zcash crates that support it is needed (RSK-14).
- **SQLite lock waits.** If another process holds the database's write lock, the console's requests wait up to 2 seconds, then fail with a retryable error, having changed nothing (RSK-22).

## Requirements

- **Rust:** 1.88 or later (`rust-version`), with `protoc` for the gRPC client.
- **Node:** 24 or later (the console's `engines`; `@zeceipt/verify` is ES modules).
- **Python 3:** for the demo server.

## Provenance

- **No binaries are attached.** Build from this tag.
- **The committed WebAssembly** (`packages/verify/pkg`) was built with `scripts/build_wasm.sh`, which remaps build paths.
  - With the toolchain the README names, a rebuild from this tag gives the same bytes (measured on macOS); the README gives the expected sha256 and `scripts/build_wasm.sh --check`. A different toolchain may not; CI reports how a Linux build compares.
  - `scripts/check_release.py` checks that it reports this version.
  - `packages/verify/test/verify.mjs` checks that it agrees with the committed test vectors and carries no local build path.
- **`@zeceipt/verify`** is to be published to npm by hand from this tag on 2026-10-10, without npm provenance (`docs/RELEASING.md` §4).
- **The tag** is an annotated git tag.
